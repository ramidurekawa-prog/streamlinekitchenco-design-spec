When SKC is wrong
Confident wrongness is the fastest way to lose operator trust. SKC must have a surface for being told it was wrong — and a behavior change when it learns it was.
3 surfaces
A · Reverification A verified action can be reopened
Risotto removal
Verified $97/wk · 4 weeks ago · Berkeley menu cleanup
Verified
Guardrails will re-evaluate against the last 4 weeks of data. If guardrails now fail, the line is removed from Verified Savings and the value reverts.
B · Pattern-of-rejection alert SKC reduces its own confidence when a category is repeatedly rejected
Labor recommendations · 2 of last 5 rejected by operator
SKC reducing labor detection confidence for this account by 10%. New labor recommendations will require manager review before surfacing.
40% rejection rate
Triggers when more than 30% of recommendations in a category have been rejected. Rejected reasons are stored in Operating Memory and used to recalibrate the detector.
C · Dispute a verification A previously verified line can be flagged as wrong
Tuesday lunch labor adjustment
Verified $42/wk · 8 weeks ago · Oakland
Verified
Why are you disputing this verification?
Disputed verifications are flagged for human review. The $/mo run-rate associated with the line is not retroactively removed from ROI without review — but it stops contributing to subscription-coverage math until reviewed.
Doctrine: SKC must surface its own wrongness, change behavior in response, and never quietly delete history. Reverification, pattern-of-rejection alerts, and dispute escalation are the three surfaces where this happens. Operators are explicitly empowered to tell SKC it was wrong.

How SKC works · what's automated, what's rules-based, what's AI
SKC is positioned as an "AI Restaurant Profit Manager." Here is exactly what that means — and what it doesn't mean.
▾
Automated · deterministic Computed by SKC from your data — no model judgment involved
  • Detection thresholds (e.g. "CM gap > 10 pts for 3+ weeks")
  • Guardrail monitoring (every service · pass/fail against limits)
  • Source freshness tracking (Toast, 7shifts, KDS, Recipe Cost, Reviews, Accounting)
  • Baseline calculation (rolling windows · weighted averages · anomaly exclusion)
  • Lost-cover math (seat-based capacity model)
  • Time-basis arithmetic (per-service → weekly → monthly run-rate)
Rules-based · logic SKC executes Deterministic decision rules — not learned, not adaptive without an explicit update
  • Recommendation ranking (by weekly exposure × confidence)
  • Action sequencing (which leak to surface first today)
  • Blocker resolution order (which DQ failure to ask the operator to fix first)
  • Verification eligibility (which monitoring windows can close into Verified Savings)
  • Approval-required gating (e.g. price changes >5% require owner sign-off)
  • FOH-action lockout when kitchen root cause is unconfirmed
AI-assisted · LLM-generated narrative only An LLM writes the words. It does not compute the numbers.
  • Evidence drawer explanatory text (the prose around the numbers)
  • "Ask SKC" responses (cite the rules engine output; never invent figures)
  • Weekly digest narrative wording (numbers plug in from the rules engine)
  • Operator memo phrasing (do this / don't change / watch / reverse if)
Doctrine: every dollar value on SKC is computed by deterministic rules, not generated by an LLM. AI is a language layer over the rules engine — it explains numbers, it never produces them. If the rules engine cannot compute a number, no narrative is generated; the surface stays empty until the rules can fire.
Why this loop improves retention Doctrine
Verified value creates renewal proof. Push digest creates habit without requiring login. GM scorecard creates internal adoption. Human value review prevents silent churn. Operating memory creates legitimate switching cost. Quarterly detectors expand value surface area.
