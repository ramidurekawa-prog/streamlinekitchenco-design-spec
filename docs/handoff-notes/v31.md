## What this version is

The first version of the spec as a **folder-structured repo** rather than a single 31k-line HTML file. Behavior is identical to v30b — same screens, same numbers, same interactions — only the file layout changed. Everything that was in `skc-demo-v30b-tooltips-floating.html` is now split into:

- `index.html` (44 lines) — just the shell + one `<script src="shared/loader.js">`
- `shared/` — CSS + JS (6 files)
- `components/` — sidebar, topbar, ask panel, drawers (4 files)
- `screens/` — one file per screen (13 files)
- `docs/` — written rationale (doctrine, canonical numbers, data sources)

See `README.md` for the full layout and how to run it (`python3 -m http.server 8000`).

## Start-here reading order

1. `README.md` — repo overview + acceptable/unacceptable divergence list.
2. `docs/doctrine.md` — the output type and state model. Every dollar value the UI shows labels itself according to this. **Read this before writing any feature code.**
3. `docs/canonical-numbers.md` — the dollar values that appear across screens. If two screens disagree, the source `OPPORTUNITIES` constant in `shared/core.js` is canonical.
4. `docs/data-sources.md` — what comes from Toast / 7shifts / KDS / operator. Includes the Server Coaching axis-state model.
5. Run the demo (`python3 -m http.server 8000`), click through every screen with `docs/canonical-numbers.md` open. The point is to develop a feel for which numbers carry which state classification.
6. Pick the highest-priority screen from the "stable" list above and start implementing.

## Known caveats in this version

- **`screen-config` is genuinely nested inside `screen-settings`** in the source HTML. We preserved this in `screens/settings.html`. In Next.js, build them as separate routes — `/settings` (Data Quality) and `/config` (Workspace) — don't replicate the nesting.
- **One pre-existing source bug was fixed during validation** (`pr-summary-strip` typo). All other behavior is identical to v30b.
- **The loader has an init-timing shim** that wouldn't exist in a real Next.js implementation. It's only there because the static HTML demo needs to compose itself at runtime; React's component model makes this a non-issue. Read `shared/loader.js` if curious, then forget about it.
