## What this version is

A **consolidation pass on the Actions feature.** The old Actions page was a
four-subpage tree (`Overview` + a 4-way `Queue` toggle + `History` + `Evidence`),
wired into a sidebar sub-tree, and every feature screen linked into it. v33
collapses all of that into **one scrollable board** matching the wireframe:

```
LIVE · TUE JUN 3, 6:42 PM · OAKLAND + 2        (status line / "Clock")
$1,229  /wk in play                            (run-rate hero — no [EST] chip)
[Undo]                    [Filter ▾] [New action]
Blocked → Ready → Monitoring → Verified        (Kanban — cards NOT draggable)
THE PROOF · $1,847 [VERIFIED] · 24 banked · 86% · $97/wk added  + 3 history rows
▸ How verification works                       (condensed doctrine)
```

**Doctrine is intact.** No `OUTPUT_TYPES` or state-machine change. The board's
numbers were taken **verbatim from the comps and registered as canonical**, but
they are **additive** — they don't revise any existing figure. `$1,229 in play`
is a new metric (Ready + Monitoring board sum) that coexists with the unchanged
`$1,243/wk Open Exposure`; `$1,847` is the new lifetime-verified bank, distinct
from the unchanged current `$420/mo · $97/wk` line; `$97/wk added this period`
**is** that canonical `$97/wk`. Full table: `docs/canonical-numbers.md`.

## Column → state mapping (read this)

The four columns map a card's status only — the client never moves a card.

| Column | Statuses it holds |
|---|---|
| **Blocked** | `blocked` |
| **Ready** | surfaced / pending / assigned (pre-implementation, actionable) |
| **Monitoring** | implemented / monitoring / ready-to-verify (active recovery) |
| **Verified** | `verified` (counts toward ROI) |

⚠ The wireframe's **"Ready" is not the old "Ready to Verify"** (which was
end-of-monitoring). Here "Ready" = ready for the operator to act. End-of-window
items live in Monitoring until they verify.

## How to implement

- **Board is read-only.** A card's column is derived from its action `status` /
  `output_type` (the doctrine state machine), never from a drag. Render the four
  columns by bucketing actions; do not add DnD.
- **Filter:** within a group OR; across groups AND. Empty group = no constraint.
  Counts reflect *visible* cards. This is the unit covered by the "filter logic"
  test ask — there's no test runner in this spec repo, so it's verified via the
  browser (see below); add the real unit test in the Next.js port.
- **Hero "in play"** = sum of the non-blocked, non-verified cards on the board
  (Ready + Monitoring). Keep it labelled "in play" + "estimated · not verified";
  never "saved". Verified savings live only in the Proof block.
- **Numbers source of truth:** `RUN_RATE_IN_PLAY` / `PROOF_LIFETIME` in `core.js`;
  the board cards are hardcoded in the markup (this is a static spec). In the port,
  back every card with a real action object and compute the hero/Proof aggregates.

  Throughput has no card in this comp; add the option when a throughput card lands.
- **Vestigial `switchTab('execution',…)` prefixes** remain in a few legacy CTAs
  (`screens/roi-proof.html`, `screens/reports.html`, Ask-panel actions in
  `core.js`). The `execution` tab group is gone, but `switchTab` is null-safe so
  they're harmless no-ops before the `showScreen('actions',…)` that follows. Safe
  to strip in a later cleanup.
- **Old CSS/JS not yet deleted.** The unused `.ac-subpage/.ac-queue/.sp-*` style
  blocks and dead helpers (`acQueueShow`, `_actionsUpdateNav`, `populateActionTabs`,
  the `navActionsChild*`/`toggleActionsNav` handlers) are left in place to keep
  this diff reviewable. Flag a deletion pass once the board is signed off.
